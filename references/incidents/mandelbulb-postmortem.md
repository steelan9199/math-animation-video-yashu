## 1. 耗时结构（诚实账）

| 环节 | 耗时 | 是否必要 |
|---|---|---|
| 场生成器原型验证 + 形态检查 | ~35 s | 必要 |
| 标定场景渲染（最终版） | **5.5 s** | 必要 |
| 480p 预览 × 4 轮 | 147 s | 必要（每轮改版重渲） |
| **720p 成片** | **48.7 s** | 必要 |
| 抽帧自检 × 7 轮 | ~5 min | **必要**（抓出 7 处缺陷） |
| **纯空转（轮询 + sleep + 两次被误杀）** | **~27 min** | ❌ **完全可避免** |
| 环境探测 / 失败重试 | ~2 min | 部分可省 |

**结论：渲染从来不是瓶颈**（7 次渲染合计 3.5 min，单次最快 5.5 s）。
瓶颈是**一次技术选型失误 + 后续的无效等待**。

## 2. 事故链：27 分钟是怎么烧掉的

时间轴（真实时间戳，来自 `_render_spawn.log`）：

```
22:59:09  SPAWN  ← 用 20 万个 Dot3D 启动标定渲染（渲染前卡死）
          ✗ 无 DONE
22:59~23:02  我误判为「慢」→ 轮询 20 次 × 10 s          = 白等 200 s
23:02~23:05  又 sleep 45 s 二次确认                     = 白等 45 s
23:05~23:09  再 sleep 45 s 三次确认                     = 白等 45 s
23:09:57  SPAWN  ← 前台重试，被 SIGTERM 杀掉
          ✗ 无 DONE
23:25:55  SPAWN  ← 改用 PMobject
23:26:00  DONE   elapsed=5.5s                           ← 同一个场景，5.5 秒出图
```

### 2.1 第一层失误：用 `Dot3D` 承载 20 万点

```python
# ✗ 20 万个 mobject —— 渲染启动阶段就再也走不完
dots = VGroup(*[Dot3D(radius=0.013, color=..., point=p) for p in P])

# ✅ 1 个 mobject —— 5.5 s 出图
pm = PMobject(stroke_width=1.9)
rgba = np.concatenate([cols, np.ones((len(cols), 1))], axis=1)
pm.add_points(np.ascontiguousarray(P), rgbas=rgba, color=None)
```

**关键认知**：这**不是「渲染慢」，是「根本没开始渲染」**。
Manim 每个 mobject 都要单独初始化/变换/排序，10 万级 mobject 把渲染前的准备阶段拖到走不完。
所以磁盘上一个帧都没有 —— 这个特征恰恰是**最快的确诊依据**，而我当时没去看。

### 2.2 第二层失误：把「卡住」当成「慢」，靠 sleep 反复确认

真正致命的不是选错图元（谁都会选错），而是**选错之后没有马上取证据，而是干等**。
`sleep 45` 写了两次、轮询写了 20 次 —— 这些都是**零信息量的等待**。

**30 秒判定法**（应该在第一分钟就执行）：

```powershell
Get-ChildItem "D:\github\math-animation-mcp\_render_tmp\" -Directory |
  Sort-Object LastWriteTime -Descending | Select-Object -First 1 |
  ForEach-Object { Get-ChildItem $_.FullName -Recurse -File | Measure-Object }
```

- 正常渲染几十秒内就会在 `media\videos\...` 下堆出成百上千个 PNG 分帧。
- **只有 `scene.py`、零媒体文件 ⇒ 不是慢，是跑不动。** 立刻停手改代码，不要等。

### 2.3 第三层失误：前台执行，调用一结束就把 Manim 带走

```
Exit Code: 1
Signal: SIGTERM
```

两次都出现这个。当时我以为是渲染失败，其实是**我的工具调用先返回/超时，
进程组被一起 SIGTERM**，Manim 渲染到一半就断了。

**铁证**：`_render_spawn.log` 里那两行 **只有 `SPAWN`、永远没有 `DONE`**。
判据：**`SPAWN` 与 `DONE` 必须成对**；只有 `SPAWN` ⇒ 被误杀，必须重跑。

**正确姿势**：`run_in_background=true` 启动 → `TaskOutput` 阻塞等待（会自动收到完成通知）。
不要用 `sleep`，不要前台。

## 3. 其他真问题（非时间浪费，但都是技术坑）

### 3.1 点云画成了「实心块」

第一版按 `r > 2` 判逃逸，结果整个球是实心的 —— 因为网格里大量「第一步就飞出去」的
外围点被当成表面点收进来了，它们在新投影下落在球体内部区域。

**修法**：只保留**首次越界步数 ≥ `min_steps`** 的点。越界越晚 ⇒ 一直被困在内部附近
⇒ 越贴近分形表面。

```python
newly = alive & (r > 2.0)
if k >= min_steps:               # 丢掉「一步就飞」的外围点
    hit |= newly
    steps[newly] = k
    rfin[newly] = r[newly]
alive &= ~newly                  # 逃逸后冻结，防 inf/NaN 污染
```

改完 8 重珊瑚轮廓立刻出来了。

### 3.2 点云像一层均匀的雾，没有体积感

**修法**：上色用 `(逃逸步数, 越界半径)` 两个量算权重 `w`，
再乘一个整体明暗因子 `(0.55 + 0.45 * w)`，让贴表面的壳层更亮。

### 3.3 不同参数的点云半径差很多，主体出框

实测：`p=2` 半径 **1.83**，`p=8` 只有 **1.15**（差 60%）。
沿用 `p=8` 的 zoom 会把 `p=2` 顶出画面。

**修法**：每个参数**各自 `project_points()` 拟合 zoom**。

### 3.4 参数扫描「看不出差别」

`p=2 / 8 / 12` 三张图肉眼几乎一样。诊断后确认点云**确实不同**，问题是**配色已饱和** ——
三个取值都被映到最亮端。

**修法**：按各形态范围归一化配色 + 加实时读数 `p = N` 强化差异。

### 3.5 四处版式缺陷（全部靠抽帧自检抓出）

| 缺陷 | 修法 |
|---|---|
| 公式压住球体 | 主体按 `cap_frac` 压到中下部，公式固定放 `FORM_Y≈1.7` 的上方空白带 |
| `θ→8θ` 公式压住标题 | 公式带与标题带要分开占位 |
| 小结卡片文字压主体 | 小结幕单独把主体再缩小（`fill=0.62, cap_frac=0.42`）后放在上半 |
| `p = N` 读数压主体顶边 | 读数移到右上角空白区 |

> **这 5 分钟抽帧是本次唯一「花得值」的等待**。7 处缺陷里有一半是代码逻辑完全正确、
> 只有肉眼看得出来的版式问题 —— 若交付出去，返工代价远大于抽帧成本。

## 4. 流程改进（下次直接照做）

1. **写点云类 3D 场景前**，先确认图元：>1 万点 → 直接上 `PMobject`，不要试 `Dot3D`。
2. **启动渲染前**，先标定：`n=112` 网格约 2 s，全片 720p 约 50 s —— 超出这个量级就怀疑选型。
3. **渲染一律后台**：`run_in_background=true` + `dangerouslyDisableSandbox=true`，用 `TaskOutput` 等。
4. **卡住 30 秒先取证**：查 `_render_tmp` 有没有帧、`_render_spawn.log` 的 `SPAWN`/`DONE` 是否成对。
5. **不要 sleep 硬等**。等待只在「已经确认它正在产出」之后才有意义。
6. **交付前清理**中间件（`_*.png` / `_*.txt` / `_*.log` / `_*_scene.py`），只留成片 + 源码。
