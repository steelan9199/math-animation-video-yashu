# 自进化与维护

> **只在改动本技能时读**。渲染任务日常执行不需要本文件。

## 一、总原则

**文档只做参考，实测才是唯一标准。** 拿到硬证据（可复现报错 / 探针输出 / 像素级自检结果 /
官方文档原文）证明某条知识有误，就当场删掉并写入已验证的，**不许拿文档硬扛实测结果**。

> **什么叫硬证据**：**你这次会话里亲自执行了某段代码/命令，并看到了真实输出。**
> 完整定义与反例见 §11.1。速记：**没跑过 = 推断，不管读过多少行源码都不算证据。**

四条推论：

1. **知识进出不对称**：进门槛严，出门槛更严。**只留经过验证的当前正确结论。**
2. **文档不是日志**：本技能**不记录"遇到过什么"，只记录"现在应该怎么做"**。
   想查历史去翻 git tag，那里有每一次提交的完整快照。
3. **一个坑只留一条**：同根因的多种表现合并成一条，不按现象分叉条目。
4. **🔢 不在文档里写会过期的数量**：「25 类图表」「15 个坑」「24/24 通过」这类数字
   一变就要全库同步改，还得占token，而读者真正需要的是**清单在哪**，不是**有几个**。
   正确写法是**指向权威清单**（如"已支持哪些图表见 §七 要点表"），让清单本身成为唯一真相。
   同理适用于：坑的条数、脚本数量、章节数、测试通过率。

**贯穿全文的立场：本技能要能自己长大。** 发现错误就改，别把"要不要请示"当成默认动作——
只有不可逆、或会削弱安全网的动作才停下来问（见 §四、§十一.2）。判断口径就一条：
**能不能靠 git 回滚 + 门禁能不能拦住**。能 ⇒ 直接改。

## 二、收录判据（五条门槛，全过才准进文档）

**这是本文件的核心。** 目的是防止文档退化成无边界的踩坑流水账——
本技能是渲染技能，一次任务可能撞上几十个警告，若来者不拒，`references/` 很快会膨胀到
读不动、检索不到、命中率崩掉。

一条知识要写进 `references/`，**必须同时满足以下五条**：

| # | 门槛 | 判据 | 反例（不准进） |
|---|---|---|---|
| **G0** | **有硬证据**（你亲自跑过，输出在终端里） | 没实跑过的一律不进 | 读几行源码就下结论、凭记忆断言 API 行为 |
| **G1** | **不可从代码直接推断** | 读一遍 API 签名或报错信息就能自己查出来的 | "`Line` 需要三个坐标"（签名里写着 `[x,y,0]`） |
| **G2** | **实测复现 ≥2 次，或单次代价 ≥3 分钟** | 偶发一次的、复现路径不稳定的 | 单次手滑参数写错、重试一次就好的 |
| **G3** | **静默失败，或失败代价为返工/白跑** | 报错清晰、一次定位到行的不算 | 语法错误、拼写错误、库未安装 |
| **G4** | **能写成一条可执行的正确做法** | 只能描述"注意这里容易错"而说不出该怎么做 | 纯情绪、纯猜测、纯 TODO |

> **G0 是总闸，其余四条管的是"值不值得写"，G0 管的是"是不是真的"。**
> 硬证据的定义、强度分级与循环论证陷阱见 §11.1。

**三条优先收录（即使 G2 边缘也收）**：

- **静默失败类**：不报错、退出码 0、但画面不对。这类最贵——因为没有任何信号提示你错了。
- **高耗时类**：卡住、干等、反复重试。判据是 30 秒内能拿到证据区分"慢"与"跑不动"。
- **本机绑定类**：与本机路径、版本、字体、缓存相关的具体事实。换个环境就失效的知识价值低。

**明确不收**（当场丢弃，不要"先记着"）：

- manim 官方文档已写明、报错信息已直说的；
- 一次性环境故障（磁盘满、网络抖、临时目录被清）；
- 只在这一个场景成立的私货写法，未在其他场景验证过；
- 任何形式的"以后可能用得上"。

**收进哪里（决定体积的关键）**：

| 内容类型 | 归属 | 理由 |
|---|---|---|
| 硬约束 / 红线（违反 = 白跑、返工、破坏合规） | **常驻 `SKILL.md`** | 漏读即事故 |
| 坑的正确做法（可 grep 的具体解法） | `references/pitfalls.md` | 命中窄、体积大 |
| 静态图路线的坑 | `references/chart-generation.md` / `wechat-cover.md` | 按路线分流，不必都读 |
| 0.21.0 的 API 查证结论 | `references/manim-api-troubleshooting.md` | 版本绑定，随用随查 |
| **单次事故的完整复盘**（耗时账、事故链、错在哪一步） | `references/incidents/<名字>.md` | 复盘是长文，只在重犯同源事故时才读 |

> **incidents 的门槛比 pitfalls 高**：坑的"怎么做"进 `pitfalls.md`；只有当某个坑
> **造成了大额时间损失**（如 27 分钟空转）才另开一篇复盘。**普通坑不许开 incident。**

## 三、删错门槛

只有**硬证据**才动手删；仅"我觉得可疑"不动手——**误删一条对的知识比留着错知识更难发现**
（错知识有痕迹，对的知识被删了就像它从来没存在过）。

**删之前先自问一句：「我要删的这条，我自己验证过吗？」**
如果当初删它靠的是"读源码推断"而不是实跑，那它可能根本不该删——
本技能历史上就犯过这类错（见 §11.1 循环论证陷阱）。
**发现疑似错误时，第一反应是跑一次验证，不是改文档。**

删的时候**删干净**：不并存、不标注、不归档，**连"曾记录 X、已推翻"这类痕迹都不留**。
想查历史去翻 git tag。

**连带禁止「负向声明」**：文档里不许出现「已废弃的旧口径」「勿再使用」「本节曾要求…现已推翻」
这类写法——它把已删掉的旧知识**原样抄回上下文**，读的人（包括 AI）等于把错误知识又收了一遍，
比不写更坏。**文档只写当前正确规则。**

自检：`node scripts/skill_audit.js` 会扫全库这类写法并列出命中行号
（本文件与门禁脚本自身豁免——必须引述这些词形才能说明禁令）。

## 四、授权分级

**默认自进化：取证充分即可直接改，不必请示。** 目的是让技能能自己长知识，
而不是每次都要人点头——卡住自进化的请示成本，比改错的成本更高。
**同一原则也适用于 MCP 仓库**（§11.2 的分级是它的细化，不另立一套口径）。

| 改动类型 | 授权 |
|---|---|
| 事实订正 / 删除已证伪的句子 / 补实测结论 / 修文档笔误 | **直接改** |
| **新增知识**（过了 §二 五道门槛）/ 改写表述 / 调结构与顺序 / 补断链与去重 | **直接改** |
| **跨多个文件的联动改动**（如同一结论在 3 份文档里都写错了） | **直接改**，改完在回复里逐个列出 |
| 动 `SKILL.md` 硬约束 / 红线 / 体量红线 / 字体白名单 | **直接改**，但回复里必须**显式说明改了什么、依据是什么** |
| 删脚本 / 删 git tag / 改推送目标（origin）/ 让门禁红灯被绕过 | **必须报备** |

只有最后一类才需要停下来问——它们都不可逆或会削弱安全网。
判断口径：**能不能靠 git 回滚 + 门禁能不能拦住**。能 ⇒ 直接改；不能 ⇒ 先问。

## 五、版本号规则

frontmatter 的 `version` 用语义化版本，**每次修改必须递增**：

| 递增位 | 适用场景 |
|---|---|
| patch（第三位） | 订正错误 |
| minor（第二位） | 新增知识 / 新增章节 / 新增自进化机制 |
| major（第一位） | 结构性重写或红线变更 |

判定：比对新旧版本号，**第一个发生变化的数字位**即递增位；一次改动跨多档按最高档算。

## 六、位次决定推不推

- patch ⇒ **只落盘、不碰 git**，攒到下次 minor/major 一并提交；
- minor / major ⇒ 视为**已获推送授权**，改完即提交推送并打 tag，**不再问**。

## 七、push / tag / 回滚纪律

1. 一律用 `node push.js "<说明>"`（等价于 `git add -A` → commit → push → tag），
   **禁止裸跑** `git add/commit/push`（裸跑靠 cwd 向上找仓库，可能命中别人的仓库）。
2. `push.js` 内置三道闸：① 仓库根 realpath 校验（`C:/Users/...` 与 `D:/CToD/...` 是同一目录的
   两个视图，**必须归一后比对**）；② `origin` 必须等于本技能仓库；③ 提交前跑本文件的复测命令，
   不过就拒推。
3. **每次 minor/major 推送必带 tag**（`v<版本>-<时间戳>`）。tag 是回滚的唯一落点：
   - 回滚看历史：`git -C <技能目录> tag`；
   - 回滚代码：`git -C <技能目录> checkout <tag> -- .`（只回滚文件，保留 git 目录）；
   - 回滚整个版本：`git -C <技能目录> reset --hard <tag>`。
4. 暂存用 `add -A`，故 **`.gitignore` 是唯一过滤网** ⇒ 新增临时目录/产物类型必须同步补进它。
5. **不记变更历史**：只维护版本号，不写 CHANGELOG（git 历史就是 CHANGELOG）。

> **⚠ 改 `push.js` 前必读：`spawnSync` 在本机一律返回 `EBUSY`，只能用异步 API。**
>
> **现象**（2026-10-07 实测）：`spawnSync` 对 `git` / `cmd` / `pwsh` / 甚至
> **一个根本不存在的可执行文件**全部返回 `EBUSY`；而同一进程内
> `await execFile("git", ["--version"])` **正常返回**。
>
> **⚠ 归因：只锁定在 `spawnSync` 这一个 API 上。不要归给环境、node 或git。**
> 下面每条都实测否掉了，别再往这些方向猜：
>
> | 曾怀疑 | 实测结果 |
> |---|---|
> | 是 git 的问题 | ✗ 不存在的可执行文件也报同样 EBUSY |
> | 是 PATH / `shell:true` / cwd / 绝对路径问题 | ✗ 四种都试过，一律无效 |
> | 是 WorkBuddy 沙箱限制 | ✗ 关沙箱（`dangerouslyDisableSandbox=true`）与独立 PowerShell 进程里同样失败 |
> | 是某个 node 构建的 bug | ✗ v22.13.1 与 v22.22.2 两个独立二进制表现完全一致 |
> | 是 Windows 限制了 git/pwsh/node | ✗ 在 pwsh 里直接敲 `git` 完全正常 |
>
> **⚠ 容易误判的地方**：在 pwsh 里敲 `git` 走的是「PowerShell → git」，**不经过 node**，
> 所以正常；而这里是「node → spawnSync → git」，卡在 node 自己的同步 API 上。
> 两者现象不同，不要混为一谈。
>
> **结论**：本机 git / pwsh / node 全部正常，**只有 `spawnSync` 这一个同步入口不可用**。
> 因此 `push.js` 的git 调用必须走异步 `execFile`，**不要改回 `spawnSync`**。
> 症状与四组对照证据都在 `push.js` 脚本注释里，改前先看那段。

## 八、复测（改完必跑，不跑等于没改）

```powershell
node scripts/skill_audit.js              # 只跑门禁，不提交不推送
node scripts/skill_audit.js --top        # 附体量 TOP 8 与断链明细
node scripts/skill_audit.js --json       # 机器可读
node scripts/skill_audit.js --save       # 记一条历史，作为下次对比基准
node push.js --check                     # 只跑门禁（不碰 git，git 不可用时也能用）
```

门禁检查四件事，任一不过退出码 1：

1. **引用断链**——`SKILL.md` 与 `references/` 里提到的文件是否真实存在；
2. **负向声明**——全库有无「已废弃 / 勿再使用 / 已推翻 / 曾要求」类痕迹；
3. **字体白名单（零容忍）**——全库只允许 `Noto Sans SC` 与 `LXGW WenKai GB` 两个名字，
   **出现在任何位置都算违规**：代码里的 `font=` / `set_font(`、文档正文、表格、注释、反例，
   一律不允许。**没有行级豁免**——想教人别写某个字体，就不要把那个名字写出来。
   扫全目录（含技能根目录，不止 `references/` 与 `scripts/`），`.js` 也扫。
4. **体量红线**——常驻 `SKILL.md`（**tok 与字符两条并列红线**：≤3300 tok 且 ≤10000 字符）
   与单篇 `references/*.md` 是否超线。

> 门禁**查不出语义矛盾**（同一件事在两处说法冲突、章节编号错位、
> 文档内嵌的代码副本与脚本本体不同步）。这类问题靠人/AI 通读比对，
> 门禁只兜住结构层。

## 九、体量红线

- **常驻层 `SKILL.md` ≤ 10000 字符，且 ≤ 3300 tok**（中文 0.75 tok/字，其余 3.5 字符/token）。
  **两条是并列红线，任意一条超线即红灯。**
  这里的"成本"不是文件大小，而是**被读进上下文的次数**：常驻层每轮对话重发一次，
  `references/` 命中才读一次。**一段内容移出常驻层，付费次数就从 N 变成 1。**
- **字符上限 10000**（2026-10-07 标定）。字符数比 tok 更直观、也能约束中英混排的总量，
  故与 tok 线并存：tok 线管"上下文成本"，字符线管"文件规模"。
- **tok 上限 3300**（2026-10-07 标定）。定这个数之前已做过一轮瘦身：6273 → 3216 tok（降 49%），
  做法是把与 `references/` 重复的复述全部换成指针。**剩下的每一条都是 T1 级**（漏读 = 白跑 /
  返工 / 破坏字体合规），再砍就要赶走事故级内容了——按本文件 §二 的判据，
  **优先压缩同层冗余，而不是把 T1 内容赶出去**。
- **余量刻意留小**：够插一行指针，不够塞一段新规则 ⇒ 用阈值逼新内容下沉 `references/`。
  当前余量**不写在这里**，跑 `node scripts/skill_audit.js` 现看。
- **单篇 `references/*.md` ≤ 20000 字符**；超了先考虑拆分，而不是继续往里加。
- **单篇 `references/incidents/*.md` ≤ 24000 字符**。
- ⚠️ **不要连续上调阈值**。调高一次就说明常驻层在膨胀，负反馈被削弱。
  **新增内容默认先下沉 `references/`**，"往 SKILL.md 加字"是需要说明理由的例外。
  确需上调时，在本节记录**沿革 + 上调理由 + 当时实测值**，并同步改 `scripts/skill_audit.js` 的 `BUDGET`。
- **⚠️ 单篇超 12000 字符的 references 必须在 `SKILL.md` 路由表标 ⚠️**，提示"先 Grep 局部读"。
  `scripts/skill_audit.js --top` 会算出这个阈值并列出命中文件。
  **路由表里不要写"体量"数字列**——那是最易过期的一类数字（见 §一.4），标 ⚠️ 就够。

## 十、备份：用 git，不用复制文件夹

**git 就是本技能唯一的备份。** 它同时提供完整历史、任意时点回滚、按版本整体回退，
`cp -r` 三样都做不到。

改动前的标准动作，**不要拷文件**：

```powershell
git -C <技能目录> status --porcelain        # 确认工作区状态，知道自己在改什么
git -C <技能目录> tag --sort=-creatordate    # 确认有 tag 作回滚落点
```

- patch 级改动：工作区本身就是"改动前状态"，**不需要任何额外备份**。
- minor/major：改完走 §七 的 `node push.js`，它会自动 commit + push + 打 tag，
  **tag 就是回滚落点**。
- 回滚：`git checkout <tag> -- .` 回滚文件，或 `git reset --hard <tag>` 回滚整版。

**只有一种情况需要临时拷贝**：没有 tag 兜底的大重构前（如跨版本重写、批量改脚本）。
此时拷一份，**改完提交后立刻删掉**——它是临时垫片，不是历史。
长期堆积 `_backup/` 与本文件 §二「文档不是日志」相悖：git tag 已经存了每一次快照，
再堆全量副本只是白占空间、让人误以为那是唯一退路。

## 十一、改 MCP 仓库的规则（`D:\github\math-animation-mcp`）

**背景**：本技能依赖的 MCP 是本机私有分叉，上游原作者已数月不更新。
**所以 MCP 的代码与文档都可能含错，错在 MCP 侧时以 MCP 侧为准**，不要为了迁就它把错误知识写进本技能。

**授权口径与 §四 一致**（取证充分即可直接改），下面 11.2 只是把分级细化到 MCP 侧。

### 11.1 取证门槛（不满足 = 不许改）

**先定义什么叫硬证据：硬证据 = 你亲自执行了某段代码 / 命令，并看到了它的真实输出。**
判据只有一条：**你这次会话里跑过它，输出就在终端里。**
没跑过就下结论 = 推断，不是证据——不管你读了多少行源码、逻辑链多完整。

| 证据强度 | 类型 | 要求 |
|---|---|---|
| **✅ 硬证据（可直接据此改文档）** | 实跑输出 | 亲自执行命令/脚本，拿到真实输出。输出必须可复现（重跑一次还是它） |
| **✅ 硬证据** | 完整 traceback | 用 `scripts/probe_charts.py`（dry_run）跑出**完整**回溯，不是 MCP 截断的 `error_msg` |
| **✅ 硬证据** | 复现记录 | 同一现象稳定复现 ≥2 次，或单次代价 ≥3 分钟（与 §二 G2 同一门槛） |
| **⚠️ 仅供定位，不足以定论** | 源码/上游对照 | 读 MCP 源码（`src/`）或 manim 源码，**用来定位在哪查**，不能替代实跑 |

**为什么源码对照不能单独定性——循环论证陷阱：**
最危险的一种误判是「读脚本第N 行的检查项，推断出脚本认为某结论成立，于是改文档」。
检查项代码与它自己的注释**同源**：两者都写错时，你从它们内部永远无法判断谁对。
必须**跑一次那个脚本**、看到真实输出，才能判定哪边是真结论。

> 实例：`check_manim_version.py` 的 docstring 曾写 `AnnularSector`「不在顶层」，
> 而脚本第 70 行的检查项是`hasattr(manim, "AnnularSector")`。读代码会得出
> 「docstring 写反了」——但这是拿"脚本声称检查什么"论证"检查结论是什么"，循环论证。
> 实跑一次得到 `AnnularSector 顶层已导出 实际 True` 才是硬证据。

**算术/计数类结论也要实算**：容量换算、图表行数、阈值比较，
一律现场算一遍或现场数一遍，不要凭印象改数字。

**禁止的"证据"**：单次偶发、单次手滑参数错、"我以前遇到过"、
`error_msg` 里截断的回溯尾部当结论、"读源码推断出的结论"、
以及"绕过去就好了所以 MCP 没问题"。

**归因不清 = 不改。** 分不清是 MCP 错、Manim 本身行为、还是本技能场景代码写错时，
**先查清归因再决定**；实在分不清就**如实告诉用户三种可能**，不要挑一个顺手的改。

**但归因清楚 + 取证充分 = 直接改，不要停在"要不要请示"这一步。**
停下来问的唯一理由是 11.2 末尾那两类不可逆动作，不是"改动有点大"。
### 11.2 可直接改 vs 必须报备

| 改动 | 授权 |
|---|---|
| MCP 内文档/README/PLAN 的事实订正、笔误、死链、失效示例 | **直接改** |
| 单个文件的局部 bug 修复（有复现证据、不改接口签名） | **直接改** |
| **跨 1 个以上文件的联动修复**（同一根因在多处表现） | **直接改**，回复里逐个列出改了什么 |
| 动渲染核心：`render_animation` / `preview_scene` / `render_gif` / 风格注入 / 风格与背景色逻辑 / 超时参数 / 输出目录 | **直接改**，但改完必须跑 11.3 的回归自检并在回复里说明 |
| 改接口签名、新增依赖、升级 manim 或其他包 | **必须报备**（影响本机 MCP 配置与 SKILL.md 调用方式，升级不可逆） |
| 删工具 / 大范围重构 / 换 remote | **必须报备**（不可逆或削弱安全网） |

判断口径与 §四 一致：**能不能靠 git 回滚**。能 ⇒ 直接改；不能 ⇒ 先问。
